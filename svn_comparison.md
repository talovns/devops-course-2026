# Шаг 4.2. Ответы на вопросы

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

В Git ветка — это просто указатель на коммит, маленький файл с 40-символьным хешем. Создать ветку значит записать один файл: ничего не копируется, всё происходит локально и мгновенно. Слияние тоже дешёвое: Git хранит полный граф истории и сам находит общего предка веток для трёхстороннего слияния.

В SVN ветка — это копия каталога в репозитории на сервере (`svn copy trunk branches/feature`). Копия «ленивая», файлы физически не дублируются, но операция всё равно идёт через сервер и требует сети. Главная «дороговизна» даже не в создании, а в слиянии. Исторически SVN плохо отслеживал, что уже было слито (`svn:mergeinfo` появился только в версии 1.5), поэтому слияния сложные и часто дают конфликты, а переключение между ветками медленное. Из-за этого в SVN ветки заводят редко, а в Git их создают под каждую задачу.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

Нельзя. SVN — централизованная система: репозиторий и вся история хранятся только на сервере, а у разработчика есть лишь рабочая копия одной ревизии. Коммит сразу отправляет изменения на сервер и создаёт там новую ревизию, поэтому без связи с сервером он невозможен. Без сети можно только редактировать файлы, смотреть `svn diff` и `svn status` относительно последней скачанной версии.

В Git же репозиторий с полной историей есть у каждого локально, поэтому `git commit` работает офлайн. Сеть нужна только для `push` и `pull`.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

- **Большие бинарные файлы** (игровые ассеты, видео, CAD-модели, дизайн-макеты). В Git каждый клон тянет всю историю всех версий, и репозиторий разрастается. В SVN клиент скачивает только нужную ревизию.
- **Блокировка файлов (lock).** Бинарные файлы нельзя слить автоматически, поэтому важно, чтобы их одновременно не правили двое. В SVN это встроено (`svn lock`, `svn:needs-lock`).
- **Частичный checkout.** Можно выгрузить только один подкаталог огромного репозитория. В Git это делается сложнее (sparse checkout).
- **Централизованный контроль доступа**, вплоть до прав на отдельные каталоги. Это важно в корпоративной и регулируемой среде.
- **Простая линейная модель** с последовательными номерами ревизий (r1, r2, r3…). Её проще понять нетехническим участникам: дизайнерам, документалистам.
- **Легаси-проекты** с многолетней историей в SVN, где миграция на Git дорогая и рискованная.
